# Tool Calling in TabbyAPI   

Tool calling is available for supported models, and enabled by selecting a tool format in the model 
config. This can also be specifed per model using `tabby_config.yml`.  

Most tool-calling models are also reasoning models, and it is recommended to enable reasoning as 
well with appropriate reasoning tags (these cannot currently be inferred from the model's template).
The parser still respects these tags even if the model does not support tool calls or no 
`tool_format` is given.  

```yml
model:
    reasoning: true
    reasoning_start_token: "<think>"
    reasoning_end_token: "</think>"
    tool_format: qwen3_5
```

### Supported formats

Below are the currently recognized tool call formats.

By default `tool_format` is `auto`: when a model loads, TabbyAPI scores every format against the
model's chat template (the literal markers it renders around a tool call), the special tokens in
its tokenizer and, as a tie-break, its architecture, and selects the unique best match. The
reasoning tags default to `auto` as well and are taken from the detected format when the template
or tokenizer confirms them, otherwise from the template alone; if none are found, reasoning parsing
is switched off for that model. The startup log reports the outcome on a `Response parsing:` line.
When no format matches a template that does define tools, the server warns and tool calls are not
parsed; set `tool_format`, `reasoning_start_token` and `reasoning_end_token` explicitly in
config.yml or the model folder's `tabby_config.yml` in that case. Setting any of them explicitly
always overrides detection.

template variables, settable per request via the top-level fields or `chat_template_kwargs`.

**⁵** LFM2 models emit a Pythonic tool-call list in `<|tool_call_start|>[...]<|tool_call_end|>`,
which the server's bundled template doesn't explicitly steer the model toward. Point the model at
the included `templates/lfm2.jinja` (`prompt_template: lfm2.jinja`) so fresh-session tool calls
reliably use that format instead of drifting to OpenAI-style JSON.
The template requires parallel tool results in the same order as the corresponding tool calls;
TabbyAPI sorts tool messages by `tool_call_id` before templating, so clients may send them in
any order.

**⁶** For the qwen3_coder family, streaming responses report tool calls incrementally: instead of a
single delta with the finished call at end of stream, the response carries `tool_calls` deltas with
partial `arguments` fragments (same `index`, `id` and `name` as before), which clients concatenate
as usual. The concatenated fragments are identical to what the end-of-stream parser produces, so
assembling deltas and reading a non-streaming response give the same result. A tool call that
generation cuts off in the middle is the one exception: its fragments stop early, while the
end-of-stream parser would drop the incomplete call entirely.

### Qwen argument and streaming contracts

Qwen XML parameters use the request's tool schema to distinguish strings from JSON values.
A parameter declared as a string keeps text such as `123`, `true` and `{"nested": [1]}`
as a string. Only the template's one surrounding line break is removed, preserving code
indentation and trailing blank lines. A string union decodes a non-string JSON
value only if that type is allowed by the schema; otherwise it preserves the raw
string. For example, `string|null` keeps `123` and `true` as strings but interprets
`null` as null. The wire format cannot distinguish the literal string `null` from
the null value in that union. Local schema references and string enums are also
recognized. This parsing is not a substitute for strict JSON Schema constrained decoding.

Literal `<think>`, `</think>`, `</function>` and `</tool_call>` inside a parameter
are preserved as argument data. The literal `</parameter>` remains ambiguous in Qwen's
wire format: it closes the parameter. Bare `<function=...>` blocks are also recognized.
An unmatched closing wrapper such as `</tool_call>` outside a call remains ordinary
content or reasoning text; a closing tag by itself cannot begin a tool call.

Each streaming choice starts with `delta.role: "assistant"`, including tool-only,
reasoning-first, and empty completions, so SDKs can reconstruct a valid assistant
message for the next turn. Streaming preserves reasoning, text and tool order when
a backend chunk spans several channels. Indices and call IDs remain stable across
argument fragments. A token-budget
stop stays `finish_reason: "length"`; partial tool arguments are never labeled a
completed tool call. A normal stop containing malformed tool markup reports a clear
generation error (HTTP 502 for non-streaming, an error event for streaming), instead of
returning `finish_reason: "tool_calls"` with zero calls or silently dropping an
incomplete second call after a completed first call. Clients should wait for the
finish reason before executing any tool assembled from streaming fragments.

With `tool_choice: "none"`, tool declarations are removed from the prompt. Requests
without tools keep code examples as text. The Qwen grammars described below enforce
`parallel_tool_calls: false` during content generation. When an automatic request
uses a different output constraint or an unconstrained phase, the parser still
returns only the first call for that setting.

Chat and text completion responses preserve a requested model ID only when it
matches the loaded model's basename, resolves to the loaded model's directory
(including a public symlink), or is an explicitly configured dummy alias. When
inline loading is disabled and an unknown name is ignored, the response identifies
the actual loaded model. Both streaming APIs use the standard `model` field,
including their final usage chunks.

### Automatic Qwen tool selection

For `qwen3_coder` and its aliases, requests with tools and `tool_choice: "auto"`
(or an omitted choice) use a grammar that permits ordinary text and zero calls.
The request remains automatic: all declared tools stay in the prompt and the
model chooses whether to call one. As in the tool parser, complete Qwen call
openers are reserved for calls when tools are supplied. Once the model emits a
complete `<tool_call>` or bare `<function=` opener, the grammar requires valid tool syntax before content
can resume or EOS can end the response. Function names must come from the
request, and `parallel_tool_calls: false` permits at most one call.

Native Qwen tool and reasoning tokens remain valid literal data inside argument
values. Conversation-boundary and EOS tokens cannot interrupt an opened call.
An explicit token budget or client stop condition can still cut generation short;
clients must check the finish reason and validate completed arguments. This is a
structural grammar, not strict JSON Schema validation of parameter values.

The automatic grammar preserves the existing reasoning settings and applies to
the content phase; it does not constrain an independently configured reasoning
phase or change `tool_calls_in_reasoning`. Explicit client grammars, regexes,
JSON constraints, response prefixes, and continued messages keep their existing
behavior and skip the automatic grammar. Other tool formats are unchanged.

### Required and named Qwen tool choices

On the `qwen3_coder` pseudo-XML format and its aliases, `tool_choice: "required"`
uses the existing llguidance output filter to require one or more complete calls
whose function names come from `tools`. A named choice limits generation to that
function. `parallel_tool_calls: false` limits the grammar to one call. This is
constrained sampling, not only a prompt hint. The selected declaration is also
passed to the chat template for a named choice.

Reasoning can precede the call when the template starts a reasoning phase. The
XML grammar starts after reasoning closes; tool examples inside thought remain
reasoning text. When the engine supports the guarded producer handoff, implicit
model EOS tokens are suppressed only during this initial required/named reasoning
phase. The verified natural or budget-forced reasoning ending restores the normal
sampler before the content grammar starts. Explicit caller stop IDs and overlapping
stop strings retain priority, and `max_tokens` remains the hard total limit. This
does not change automatic tool selection, execute tool examples inside thought,
or guarantee that generated argument values match the user's intent. Older engines
without the guarded handoff keep their existing behavior.

Content is limited to the calls and a small amount of layout
whitespace. Parameter values retain literal markup other than their own
`</parameter>` delimiter. The grammar constrains call structure, names, and count;
it does **not** provide strict JSON Schema validation of all argument values.

For an explicitly empty object schema with `type: "object"`,
`properties: {}` and `additionalProperties: false`, both automatic and forced
content grammars disallow parameter tags for that function. A no-argument call
therefore closes immediately and parses as `{}`; an invented `__noargs` or any
other parameter is not an allowed completion. This applies to wrapped calls,
bare function openers and native function tokens. Empty properties without
`additionalProperties: false`, or nonempty `patternProperties`, retain their
existing parameter behavior. This narrow structural constraint does not add
strict validation for other schemas or for calls made inside an unconstrained
reasoning phase.
Applications must still validate arguments against their tool schema.

Forced choices require tools and a supported format. Unknown function names,
duplicate declarations, and combinations with another output grammar,
`response_format` other than `text`, `response_prefix`, or
`continue_final_message` return HTTP 400 with an explanation. Other tool formats
currently accept `auto` and `none`; a forced choice receives HTTP 400 instead of
being silently ignored. A missing or broken llguidance installation reports the
backend's grammar error instead of falling back to unconstrained sampling.

Streaming validates a function name and the call-count limit before emitting its
first delta, and both response modes check the completed result. A backend or
parser failure cannot return a successful forced response with absent or wrong
calls. Non-streaming failures return HTTP 502; a failure after streaming begins
is an error event. Clients must wait for the final finish reason before executing
a tool: exhausting `max_tokens` returns `length`, including when only partial
argument deltas were emitted.

Large Qwen string arguments are accumulated as fragments, with bounded delimiter
and whitespace holdback. The streamer joins the complete argument for final
verification, instead of copying the entire value for every new chunk. The CPU-only
microbenchmark `python -m tests.bench_tool_stream` checks exact output equality and
reports parser timings for increasing argument sizes; these are not GPU decoding
throughput measurements.

Both Qwen grammars derive added-token IDs from the active tokenizer; Qwen's
`special: false` added tokens still need token references in llguidance. To
verify a tokenizer without loading model weights, run
`python -m tests.check_qwen_tool_tokenizer /path/to/tokenizer.json`. This checks
the actual next-token masks, literal markup, named and parallel restrictions,
automatic plain-text and zero-call responses, and EOS handling. It also checks
that a captured synthetic argument prefix permits literal `<think>` while blocking
conversation-start and premature EOS tokens, and records the tokenizer SHA-256
in its JSON output.
