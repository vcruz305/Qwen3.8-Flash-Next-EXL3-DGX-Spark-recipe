## Producer timeline extension

The additional `install_phase_hooks` wrapper records existing synchronous `_advance_token_budget`, `_token_budget_can_end`, `constrain_output_now` and `set_generation_phase` events only while a matched original request is active. It finds that request by its existing native job identity, never by generated text. The timeline is capped at2048 events per request; overflow sets an explicit drop counter and invalidates capture. Disk publication remains after the collector finishes. The raw-file set remains the eight records and the observer manifest.

`sample_processed_before_budget` and `sample_processed_after_budget` record the existing Python token ID and EOS flag after normal native sample/filter/stop/rewind processing. These names intentionally do not promise every ID belongs to final accepted output. Check `checkpoint_rewound`, `new_tokens` (healing can be nonpositive), EOS and native position counters before reconstructing an accepted prefix. A guard's parser snapshot before its call may lag newly processed tokens; use its after-state to attribute protected tool/partial-tag state. A phase-change call and result are bracketed inside the sample event that triggers it. Forced output is observed separately from a natural marker. Ordinary output after the watcher disarms remains available through the existing native/full-response strings.

The earlier raw records alone distinguish three values already wrong before their first closing marker from five records whose first closing marker appears while describing a quoted value. They do not directly record callback timing or establish whether that quoted marker was intended to end reasoning. This extension measures those events without changing the eight requests or imposing a new quote/line heuristic.

`validate_timeline(trace)` performs pure structural checks: nonempty bounded events, zero drops, ordered times/indices, typed state, matching nested calls/returns/errors. It does not require a phase transition or semantic success. Missing closure can itself be evidence. The six actual engine24 CPU source scenarios (natural, forced, protected, callback error, guard error, banned-prefix rewind) produce identical output/state/errors with observation enabled or disabled. Unrelated jobs are ignored and the cap/drop counter is tested. The validator passes seven valid examples and rejects twelve corrupted examples. All these are CPU mechanics checks, not model-generation results.
