## Why

Bring the Spark fork onto upstream ExLlamaV3 1.6.0 while retaining its GB10 flat-K/mixed-K support, and make the recipe's update reproducible against the existing model packs. The initial merge compiled and passed isolated kernel checks, but fixed-input whole-model comparisons found several changes in numerical behavior. This branch includes the compatibility controls and targeted fixes needed to qualify the serving configuration; it does not claim that every upstream numerical change is a mathematical defect.

The detailed experiment history, measured settings, rejected candidates and final deployment status belong in the recipe's [2026-10-08 validation report](https://github.com/vcruz305/Qwen3.8-Flash-Next-EXL3-DGX-Spark-recipe/blob/main/VALIDATION_2026-10-08.md). That report is being finalized alongside this PR.

## Changes

- Merge upstream 1.6.0 through `151539c77abc7ab7425d30da7a4e8e3c5c154e7b`, preserving the fork's GB10 loaders, mixed-K MoE and generalized-ring paths.
- Fix MTP cache continuity when one missing hidden carry pauses drafting for a batch. Keep asynchronous device-draft position uploads immutable until the final readback, preventing reuse of pinned host values before the GPU consumes them. Clear stale embedding mirrors on reload.
- Preserve the historical FP16 normalization-fold rounding when constructing int8 generalized-ring tables. Test the old-source operation order independently.
- Add optional MTP row budgeting, defaulting to zero/unlimited, including correct cache maintenance for zero-proposal rounds.
- Add three opt-in numerical compatibility controls. `EXL3_GDN_CONV_BF16_PRODUCT=1` retains the old BF16 convolution-product rounding; `EXL3_ATTN_DECODE_LEGACY_SPLITS=1` keeps packed decode rows while restoring the old occupancy/split plan and combine precision contract; `EXL3_GEMM_LEGACY_TILES=1` restores the old CUDA automatic small-row tile candidates and cache-key domain. All default off. Existing forced GEMM shape selections remain available.
- Add optional `Job/AsyncJob.set_token_budget(max_tokens, output=None, *, end_token_id, on_end=None, can_end=None)` and `clear_token_budget()`. An already-active phase is bounded at accepted producer token positions, independent of consumer backpressure. A read-only producer guard protects tool arguments and partial opening tags. Approved forced closure drains the complete tail, then synchronously restores the next phase's constraints before another sample. Natural end markers remain pending while a banned hold can still rewind them. Stops, token healing, rewind and requeue retain their normal semantics. Guard/callback failure ends only that job and does not train draft confidence or publish an MTP continuation. With `max_tokens=None`, the same guarded contract observes a natural ending without imposing a cutoff or encoding forced output; `AsyncJob.supports_natural_token_budget` negotiates this capability. Jobs without an observer retain the existing sampling path.

The finite-budget API addresses an observed request with the same 24-token reasoning budget closing at producer counts 24 or 28 depending on streaming timing. The natural-only mode fixes the same constraint-handoff gap for ordinary unbudgeted reasoning: a raw closing-tag trigger could activate a content grammar on a literal `</think>` token inside an open tool argument. Actual Job/Filter/Tabby-parser CPU composition reproduced that failure before the guarded follow-up. It contains no prompt-specific text or model-specific token IDs. The companion Tabby change uses an independent copy of the authoritative incremental parser, synchronized from accepted CPU token IDs and reversible checkpoints. It only claims support for an already-known phase with one native end token and compatible parser framing; other formats retain their documented fallback.

## Validation and selected configuration

Validation ran on the actual DGX Spark (GB10, 48 SM, ARM64, CUDA 13, Torch 2.13.0+cu130) against the user's original flat 3.05/4.05, SAGE 4.15 and Cyber-Frost 3.87 packs. Source SHAs, settings, model metadata and preserved autotune-cache identity accompany the results.

- Native GPU checks cover merge dispatch, actual H2560/I640 generalized-ring shapes, old-source BF16 convolution output/state, FP16 and Q8 attention, delayed-stream mixed-K NOSYNC buffer/count reuse, and eager/capture/replay GEMM results for all row counts 1–32. Compatibility outputs match their saved historical controls; disabled modes match the prior candidate controls.
- Fixed-input, target-only quality checks compare each candidate with the original `94ba01d` runtime along the same cache path, separately from cache-free prefill. They use saved teacher-forced IDs, explicit recurrent rollback and Q8/FP16 cache metadata, with unique-prefill aggregation separated from q1/q6 decode. The predeclared NLL/high-confidence-error limits were retained throughout; KL alerts prompted investigation.
- Final Q8 target-only checks pass the unchanged core gates with zero remaining investigation alerts for all four packs at prefixes 255/1023/4095. Batch-four checks cover the flat 3.05 and SAGE packs. The one-variable `EXL3_MOE_COOP_KSPLIT=1` control recovered the flat batch-four result bitwise: 2,304 paged positions and 1,152 unique-prefill positions, with zero NLL/KL or high-confidence-error delta.
- The selected recipe combines the compatibility flags with existing `EXL3_GDN_PROJ_FP32=1`, `EXL3_GDN_CONV_TOKEN_MAJOR=0` and `EXL3_MOE_COOP_KSPLIT=1`. Mixed-K CoopMK remains disabled; validated `EXL3_MOE_MIXEDK_NOSYNC=1` avoids the eligible count readback while preserving the selected arithmetic.

Historical failures are retained in the experiment record: the bare merge changed prefill/decode behavior; restoring only the attention split plan did not restore its combine rounding; enabling CoopMK failed SAGE quality gates; the new uniform shared-expert K-split selection changed flat q1/batch-four behavior. These were isolated with source-faithful controls before choosing compatibility settings. Completed primary API controls on `16ca20d2`/`f4` measured mixed-K NOSYNC decode gains of 6.4–10.4%, and MTP row-budget8 improved 3.05 aggregate end-to-end throughput by 37.8% at two requests and 36.9% at four. Larger prefill chunks improved 12k prefill throughput by 20.2% with a 4.98% decode tradeoff. These measurements remain tied to their historical source/settings; final source and selected settings require the separate live replay. Kernel correctness alone establishes no speed claim.
